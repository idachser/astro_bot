# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Telegram bot (aiogram 2.x, long polling) that serves upcoming celestial events, on demand and as a weekly Saturday broadcast. Event data comes from the `skyevents` HTTP API — a standalone celestial-events service (separate repository, deployed on its own, computed with Skyfield + JPL DE440s ephemerides) that the bot reaches over the shared `astronet` docker network via `SKYEVENTS_URL` only. **The bot does not store events** — it reads them live per request, cached in memory for an hour. SQLite holds the `users` table and nothing else. PLAN.md documents the migration history (off HTML scraping, then off the In-The-Sky.org iCal feed onto `skyevents`, then off the bot's own event copy).

## Commands

```bash
uv sync                            # deps (creates .venv)
uv run python -m astro_bot         # run the bot
uv run pytest                      # tests (offline, use fixtures)
uv run flake8 astro_bot tests      # lint
docker compose up -d --build       # deploy (db and log persist in ./data/)
```

CI/CD: `.github/workflows/ci-cd.yml` runs flake8 + pytest on every push/PR; pushes to `main` then deploy to the server over SSH (git pull + compose rebuild), gated on green tests.

Python is pinned to 3.11 (`.python-version`): aiogram 2.x requires aiohttp <3.9, which does not build on 3.12+. Upgrading to aiogram 3 would lift this.

Requires a `.env` in the repo root: `TELEGRAM_BOT_TOKEN`, `DB` (SQLite filename), `NASA_IMAGE_OF_THE_DAY_TOKEN` (for "Image of the day"; NASA's `DEMO_KEY` works for light use). Logs go to `astrobot.log` (overwritten each start).

## Architecture

Three layers, one direction of imports: `handlers/` → `services/` → `db.py`.

- **`__main__.py`** builds Bot/Dispatcher, runs `init_storage()`, calls each handler module's `register_handler_*(dp)`, and starts `autosend_events.scheduler(bot)` as a background task before polling.
- **Handlers match button text, not slash commands.** The reply keyboard in `keyboards/reply_keyboard.py` shows buttons ("Week", "Today", …) and each handler filters on `Text(equals=...)`. The only real slash command is `/start`. `specific_date.py` registers a catch-all message handler (free-text "July 15" lookups), so it must be registered last. It parses against `LEAP_YEAR`, not a bare `%B %d` — strptime defaults the year to 1900, a common year, which rejected "February 29" before the user's own year could be consulted. The year is only known inside `get_day_message` (it is the user's local one), so an impossible date surfaces from `day_picker` as `DateNotThisYear`, deliberately narrower than `ValueError`: the handler must not report an event-parsing failure as a bad date.
- **Data flow:** `services/skyevents.py::fetch_range(start, end)` asks `GET /v1/events` for `start <= dt_utc < end` (`end` exclusive, as the endpoint defines it) and returns `(dt_utc, summary, description, url)` rows ordered by time — the exact shape the templates render, so nothing downstream parses or reshapes it. It returns **`None`, never `[]`,** when the service could not answer: network error, non-2xx (it answers 503 while a year generates), `coverage: null`, or an unexpected payload. That distinction is load-bearing all the way up: `services/events.py` propagates `None`, and `get_day_message` renders `EVENTS_UNAVAILABLE_MESSAGE` instead of `NOTHING_NEWS_FOUND` — an outage must never be reported as a quiet sky. `get_events_on_day` asks for every UTC date the user's local day touches (two, or three across a DST shift) and cuts to the exact instants in Python, since a local day is not a whole UTC day.
- **No event storage, by decision.** The bot used to keep a synced SQLite copy with uid-keyed upserts and phantom pruning. It was dropped because it bought nothing: the API window *is* the bot's query, skyevents' `needed_years()` is the same rule the bot used, `specific_date.py` only ever resolves dates into the current year (so there is no archive to keep), and skyevents regenerates a year roughly weekly — which shifts date-based uids and made pruning a chore rather than an edge case. The accepted cost is that a cold or unreachable skyevents means "try later" rather than stale-but-present data. Don't reintroduce a store without revisiting that tradeoff.
- **Timezones and location:** `/start` stores the user's IANA timezone plus lat/lon (from a shared location via `timezones.py::zone_for_location`; empty/NULL for "Default time"). That helper keeps the `TimezoneFinder` in a module-level singleton and the handler calls it through `asyncio.to_thread`: the constructor maps the boundary data and costs ~0.7s against ~2µs for a lookup, so building one per shared location stalled the whole bot for most of a second. timezonefinder covers open water too (`Etc/GMT±N` at sea), so a shared location effectively always resolves to something `resolve_timezone` accepts. All six day views go through one call, `get_day_message(user_id, pick_day)`: it reads the profile once and hands `pick_day` the user's local today (`timezones.py::today_in`), which returns today itself, a neighbouring day, or a date the user typed — and gives the day back for the week keyboard. A "day" is therefore the user's local day (computed as a UTC window) with event times labeled in the local zone. Don't resolve the profile in a handler to pick the day: that is both a second DB round trip and a blocking read on the event loop. `timezones.py::resolve_timezone` falls back to UTC on empty/unknown names, and `timezones.py::is_date_only` is the single home of the "midnight UTC = date-only event" convention.
- **Weather footers:** `services/weather.py` asks Open-Meteo (no API key) for hourly cloud cover and visibility at the user's stored coordinates; day messages get an "Observing conditions" footer for upcoming timed events within 7 days. Forecasts are cached in memory for ~1h (expired entries pruned on access); API failures and null hourly values just drop the footer, never the message. Day handlers run `get_day_message` via `asyncio.to_thread` — the weather HTTP call must never block the event loop, keep it that way. Because of that `to_thread`, `_cache` is shared across worker threads: every read, prune and write goes through `_cache_lock`, or a concurrent insert blows up the prune's iteration with `RuntimeError: dictionary changed size`. The Open-Meteo request itself deliberately stays *outside* the lock — holding it across a 10s call would stall every other user, and the cost is only that two threads may fetch the same day at once. The "Weather data by Open-Meteo.com" line is a CC-BY license requirement — keep it.
- **Week pagination is stateless:** the `<`/`>` inline buttons carry both the window and the target day as `week_<anchor>_<YYYY-MM-DD>` in callback_data, wrapping within the seven days starting at `anchor`. The "Week" button anchors to the shown day's Monday (Mon↔Sun); the Saturday digest anchors to itself, because it lists `today..today+6` and Monday-anchored arrows would page through five days it never mentioned while leaving five of its own unreachable. `parse_week_callback` still accepts the older bare `week_<YYYY-MM-DD>` and anchors it to Monday — those keyboards live on in chat histories after a deploy.
- **All user-facing text lives in `templates.py`** (HTML parse mode; escape event text with `quote_html`). Events carry an empty `url` (skyevents emits no links), so the day view renders the summary **bold** when `url` is empty instead of a broken `<a href="">`. The greeting and digest footer credit "Skyfield and JPL DE440s" — accurate provenance, not a license requirement (JPL is public domain, Skyfield MIT), so it can change freely.
- **Caching:** both HTTP services (`skyevents.py`, `weather.py`) use the same in-memory cache shape — module `_cache` dict, `threading.Lock`, ~1h TTL, expired entries pruned on access, failures never cached, and **the HTTP request made outside the lock** (holding it across a slow call would stall every other user; the cost is only that two threads may fetch the same key at once). The lock is not optional: day handlers run through `asyncio.to_thread`, so worker threads share the dict, and an unlocked concurrent insert blows up the prune's iteration with `RuntimeError: dictionary changed size`. Keep any third cache the same shape.
- **The Saturday broadcast** (`handlers/autosend_events.py`) fires at a fixed UTC slot (`DIGEST_HOUR_UTC`): the scheduler sleeps until `next_digest_time` instead of waking daily to ask whether it is Saturday. That older shape broadcast the instant the process started on a Saturday — and CI rebuilds the container on every push to `main`, so a Saturday deploy sent every user a second copy at whatever hour it landed — and it drifted, since a flat 24h sleep plus up to 21 minutes of fetch retries pushed the slot later every week. **Two mechanisms, both load bearing:** sleeping to a slot alone would make a restart that spans the slot skip the week silently, so startup also catches up when `missed_digest_slot` says the slot passed less than `DIGEST_CATCHUP_HOURS` ago. A clock alone cannot tell "was down through the slot" from "sent, then got redeployed", and guessing "send" turned a Saturday crash loop or a second CI push into N copies for every user — so `services/digest_state.py` records the slot that last went out in a one-line file next to the DB (`DIGEST_STATE_FILE`, in the mounted `./data/`; **not** a table — the schema stays users-only, and this is scheduler state). The marker is written only after a broadcast really goes out, so an outage or a quiet week leaves the slot open for a retry, and `send_weekly_digest` returns a bool for exactly that. Both reads and writes swallow their errors: the marker can only ever *suppress* a send, so losing it costs one duplicate, while raising would kill the only broadcaster. Drop the marker and the catch-up multiplies copies; drop the catch-up and a deploy across the slot loses the week. The loop also re-checks the wall clock after waking, since `asyncio.sleep` is monotonic and a backward clock step would otherwise re-fire the same slot. Each send is wrapped in try/except so users who blocked the bot don't kill the scheduler loop, and the loop guards the whole digest for the same reason — the scheduler task is the only thing that ever broadcasts and would die unnoticed behind healthy-looking polling. Its fetch is the one read that retries (`DIGEST_RETRY_DELAYS`): a user who gets "try later" presses the button again, a missed broadcast is missed for a week. An unreachable service sends nothing at all — never a "no events" digest to everyone.
- Tests in `tests/` run offline: the `skyevents` client is tested with a monkeypatched `requests.get` (`tests/test_skyevents.py`), everything above it against a fake `fetch_range`, and DB code against temp files (service functions accept a `db=` path override).
